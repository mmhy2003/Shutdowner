# Shutdowner — Remote Windows Power Control

**Date:** 2026-08-01
**Status:** Approved design

## Purpose

A single Go binary that runs as a Windows service on a personal PC and serves a
password-protected web UI for shutting down, restarting, sleeping, and
hibernating that PC from anywhere on the internet.

Scope is one machine per instance. Waking the machine is explicitly out of
scope: the app runs on the PC it controls, so it cannot start a machine that is
already off.

## Decisions

| Question | Decision |
|---|---|
| Access | Public subdomain over the internet |
| Ingress | Cloudflare Tunnel; app binds loopback only |
| TLS | Terminated at the Cloudflare edge |
| Actions | Shutdown, restart, sleep, hibernate |
| Wake | Out of scope |
| Auth | Single password, no username, no TOTP |
| Safety | Confirm dialog, then an abortable countdown |
| Force close | `/f` by default, opt out per action |
| Run mode | Windows service, LocalSystem, auto-start |
| UI | Server-rendered templates plus a live status panel |
| Frontend | `html/template` + vanilla JS, embedded; no Node toolchain |

## Architecture

```
  browser
     │  https://pc.example.com
     ▼
  Cloudflare edge          TLS terminates here
     │  outbound-initiated tunnel
     ▼
  cloudflared.exe          on the Windows PC
     │  http://127.0.0.1:8080
     ▼
  shutdowner.exe           Windows Service, LocalSystem
   ├── internal/web        auth, handlers, middleware, embedded UI
   ├── internal/action     countdown state machine
   └── internal/power      shutdown.exe / powrprof.dll
```

No socket listens on a routable interface. The tunnel is the only inbound path.
Running as LocalSystem means `SeShutdownPrivilege` is already held, so no token
privilege adjustment is needed, and the service is available before any user
logs in.

## Package layout

```
cmd/shutdowner/main.go       flags, service-vs-console dispatch, wiring
internal/config/             .env loading, validation, fail-fast
internal/auth/               password verify, signed sessions, rate limiting
internal/action/             schedule, countdown, abort, execute
internal/power/
    controller.go            Controller interface, Action type, Capabilities
    windows.go               //go:build windows
    unsupported.go           //go:build !windows, returns ErrUnsupported
    fake.go                  test double, also backs --fake-power
internal/sysinfo/            hostname, OS build, uptime (build-tagged)
internal/web/                handlers, middleware, templates/, static/
internal/winsvc/             service install/run wrapper (build-tagged)
```

Each package has one responsibility and a narrow interface. `web` depends on
`auth`, `action`, and `sysinfo`; `action` depends on `power`; `power` depends on
nothing. Dependencies point one direction, so every layer above `power` is
testable on Linux.

### Path resolution

`.env` and the log file resolve relative to `os.Executable()`, never the working
directory. A LocalSystem service starts in `C:\Windows\System32`; a relative
path would look in the wrong place and silently fall back to defaults.

## Authentication

### Password

`.env` holds a bcrypt hash at cost 12:

```
SHUTDOWNER_PASSWORD_HASH=$2a$12$...
```

`shutdowner.exe --hash-password` prompts without echo and prints the line to
paste. Startup fails if the value is absent or is not a well-formed bcrypt hash,
so there is no configuration that silently disables auth.

Hashing does not defend against someone who can already read `.env` — that
person owns the machine. It defends against the leak paths that actually occur:
a screenshot taken while editing config, a synced backup, an accidental commit.
bcrypt's cost also puts roughly 100 ms in front of each guess.

### Sessions

Stateless signed cookies:

```
base64url(payload) "." base64url(HMAC-SHA256(payload, secret))
```

The payload carries issue time, expiry, and a 16-byte random nonce. The secret
is `SHUTDOWNER_SESSION_SECRET`, 32 random bytes hex-encoded, generated by
`--init`.

Server-side session storage was rejected: rebooting the PC is the app's primary
feature, and an in-memory map dies with every reboot, logging the user out each
time they use it. Signed cookies survive restarts with no storage. Rotating the
secret invalidates every session, which is the only revocation a single-user app
needs.

Cookie attributes: `HttpOnly`, `Secure`, `SameSite=Strict`, `Path=/`,
`Max-Age` matching the configured TTL. Default TTL is 168h (7 days) so that a
long password is not retyped on a phone keyboard several times a day.

Verification compares the HMAC with `hmac.Equal` and rejects on any of: malformed
structure, signature mismatch, or expiry in the past.

### CSRF

`SameSite=Strict` blocks cross-site submission. On top of that, a per-session
token derived as `HMAC(secret, nonce + "csrf")` is rendered into the page and
required on every state-changing request, compared with
`subtle.ConstantTimeCompare`. Requests missing or failing the check get 403.

The token is accepted from either an `X-CSRF-Token` header or a `csrf_token`
form field, so both the JSON endpoints and the plain-form logout work. The CSP
forbids inline script, so the form-field path is what keeps logout functional
without a script block.

`POST /login` is exempt, because no session — and therefore no token — exists
yet. Forging a login for a single-user app grants the attacker a session as
themselves, which is worth nothing.

### Rate limiting

Behind the tunnel every request originates from `127.0.0.1`, so per-`RemoteAddr`
limiting would treat the whole internet as one client. The client IP is taken
from the `CF-Connecting-IP` header, which is trustworthy here precisely because
the listener is loopback-only and cloudflared is the only process that can reach
it. If the header is absent, `RemoteAddr` is used.

- up to 5 failed logins per IP per 15-minute sliding window are allowed; the 6th
  and any further attempt within the window get 429 with `Retry-After`
- up to 20 failed logins globally per 15-minute window; beyond that all clients
  get 429
- every failure logged with client IP and timestamp

A rate-limited login re-renders the login page with an explanatory message and a
429 status, rather than returning a bare JSON error to a form submission.

The global ceiling is a deliberate accepted trade: an attacker can lock the owner
out for up to 15 minutes, and the fallback is physical access to the PC.

### Response headers

Applied to every response by middleware:

```
X-Frame-Options: DENY
X-Content-Type-Options: nosniff
Referrer-Policy: no-referrer
Content-Security-Policy: default-src 'none'; script-src 'self'; style-src 'self';
                         img-src 'self'; connect-src 'self'; form-action 'self';
                         base-uri 'none'
```

`connect-src 'self'` is required: with `default-src 'none'` it is what permits the
status-polling `fetch` calls.

The CSP forbids inline script, so client JS is served as a file rather than
embedded in a `<script>` block.

## Action lifecycle

`internal/action.Manager` holds all state behind a mutex.

```
Idle ──Schedule()──► Pending{id, action, force, firesAt}
 ▲                        │                      │
 │                     Abort(id)              timer fires
 │                        │                      ▼
 └────────────────────────┴───────────────── Executing ──► Failed{err}
```

- `Schedule(action, force)` is permitted from `Idle` and from `Failed`. From
  `Pending` or `Executing` it returns a conflict error, surfaced as HTTP 409.
  Exactly one action may be pending at a time.
- `Schedule` returns an unsupported error, surfaced as HTTP 400, when the action
  is sleep or hibernate and the corresponding `Capabilities` field is false.
  Shutdown and restart are always available and are not capability-gated.
  Rejecting up front beats failing 45 seconds later.
- `Abort(id)` only cancels when the id matches the pending action, so a stale
  browser tab cannot cancel an action queued after its page was rendered.
- `Failed` retains the underlying error text. It clears when a new action is
  scheduled, and otherwise reverts to `Idle` automatically after 60 seconds, so
  no dismissal endpoint is needed.
- The timer is `time.AfterFunc` behind an injectable seam so tests fire it
  immediately instead of waiting for real time to pass.

### Countdown ownership

The countdown lives in the Go app, not in `shutdown.exe /t`. Windows cannot
cancel a pending sleep or hibernate, so `shutdown /a` would provide Abort for
only two of the four actions. Owning the timer makes all four behave identically.

The accepted cost: an action pending when the service crashes or is stopped is
lost rather than executed. Failing toward "the PC stays on" is the safe
direction.

### Suspend semantics

`SetSuspendState` blocks until the machine resumes. Sleep and hibernate therefore
remain in `Executing` across the suspension and return to `Idle` when the call
returns after resume. Shutdown and restart never return — the process is killed
mid-call, which is the only possible outcome.

## Power layer

```go
type Action string

const (
    ActionShutdown  Action = "shutdown"
    ActionRestart   Action = "restart"
    ActionSleep     Action = "sleep"
    ActionHibernate Action = "hibernate"
)

type Capabilities struct {
    Sleep     bool
    Hibernate bool
}

type Controller interface {
    Execute(ctx context.Context, a Action, force bool) error
    Capabilities(ctx context.Context) (Capabilities, error)
}
```

Windows implementation:

| Action | Mechanism |
|---|---|
| Shutdown | `shutdown.exe /s /t 0`, plus `/f` when forcing, `HideWindow: true` |
| Restart | `shutdown.exe /r /t 0`, plus `/f` when forcing, `HideWindow: true` |
| Sleep | `powrprof.dll!SetSuspendState(hibernate=0, force, wakeEventsDisabled=0)` |
| Hibernate | `powrprof.dll!SetSuspendState(hibernate=1, force, wakeEventsDisabled=0)` |

`shutdown.exe` is used for shutdown and restart because its `/f` semantics are
exactly the required behaviour and are well tested by Microsoft. Sleep and
hibernate use the API directly because the widespread
`rundll32 powrprof.dll,SetSuspendState 0,1,0` form hibernates instead of sleeping
whenever hibernation is enabled, and so cannot distinguish the two actions.

Capabilities come from `GetPwrCapabilities` in `powrprof.dll`, reading
`SystemS3` and `HiberFilePresent`. `powercfg /a` is rejected because its output
is localized and parsing it breaks on non-English installs.

Argument construction is a pure, exported-for-test function:

```go
func buildShutdownArgs(a Action, force bool) []string
```

so flag logic is unit-tested on Linux even though the surrounding
`exec.CommandContext` is not.

The `!windows` build returns `ErrUnsupported` from both methods with empty
capabilities, letting the whole server build and run on Linux for development.
`--fake-power` substitutes the fake controller, which reports both capabilities
as true and logs actions instead of executing them.

`internal/sysinfo` is split the same way. On Windows it reads the hostname via
`os.Hostname`, the OS build via `RtlGetVersion`, and uptime via `GetTickCount64`,
all through `golang.org/x/sys/windows` rather than shelling out. The non-Windows
build reports the hostname, `runtime.GOOS` as the OS string, and uptime measured
from process start, so the dashboard shows plausible values during development.

## HTTP API

| Method | Path | Auth | Behaviour |
|---|---|---|---|
| GET | `/` | session | Dashboard; 302 to `/login` without a valid session |
| GET | `/login` | none | Login form; 302 to `/` if already authenticated |
| POST | `/login` | none | Verify password, set cookie, 302 to `/` |
| POST | `/logout` | session | Clear cookie, 302 to `/login` |
| GET | `/api/status` | session | Status JSON (below) |
| POST | `/api/action` | session + CSRF | `{action, force}` → 202 `{id, remainingSeconds}` |
| POST | `/api/abort` | session + CSRF | `{id}` → 200, or 409 if nothing matching is pending |
| GET | `/healthz` | none | 200, empty body, for tunnel health checks |
| GET | `/static/*` | none | Embedded CSS and JS |

`/api/status` response:

```json
{
  "hostname": "DESKTOP-7F2K",
  "os": "Windows 11 (build 22631)",
  "uptimeSeconds": 308412,
  "localTime": "2026-08-01T21:47:03+03:00",
  "capabilities": { "sleep": true, "hibernate": false },
  "state": "pending",
  "pending": {
    "id": "b1f3...",
    "action": "shutdown",
    "force": true,
    "remainingSeconds": 38
  },
  "error": ""
}
```

`state` is one of `idle`, `pending`, `executing`, `failed`. `pending` is null
unless `state` is `pending`. `error` is populated only when `state` is `failed`.

`remainingSeconds` is sent as a relative value rather than an absolute timestamp,
so a phone with a skewed clock still renders an accurate countdown.

## User interface

Server-rendered `html/template`, CSS and JS served as files, everything embedded
with `embed.FS`. No build step and no Node toolchain.

```
┌──────────────────────────────────────┐
│  DESKTOP-7F2K              ● online  │
│  Windows 11 · build 22631            │
│  up 3d 14h · 21:47 local             │
├──────────────────────────────────────┤
│   Shut down          Restart         │
│   Sleep              Hibernate       │
├──────────────────────────────────────┤
│  Shutting down in 38s     [ Abort ]  │
└──────────────────────────────────────┘
```

- Actions unavailable per `Capabilities` render disabled with the reason as a
  tooltip.
- Clicking an action opens a confirm dialog containing a "Close apps gracefully"
  checkbox, unchecked by default. Unchecked means `/f` is passed.
- The countdown row appears only while an action is pending.
- The client renders the countdown locally with `setInterval` and polls
  `/api/status` every 3 seconds, so an action scheduled or aborted from another
  device appears on this one.
- Once a shutdown or restart fires, status polling begins to fail. After two
  consecutive failed polls following a fired action, the UI shows "PC is offline"
  as confirmation rather than a connection error. Two failed polls with no action
  pending show "Cannot reach PC" instead.
- Mobile-first layout: buttons are large tap targets, single column below 600px.

## Configuration

`.env`, beside the executable, overridable with `--config`:

```
SHUTDOWNER_PASSWORD_HASH=$2a$12$...    # required
SHUTDOWNER_SESSION_SECRET=<64 hex>     # required
SHUTDOWNER_LISTEN=127.0.0.1:8080
SHUTDOWNER_DELAY_SECONDS=45
SHUTDOWNER_SESSION_TTL=168h
SHUTDOWNER_LOG_FILE=                   # default: shutdowner.log beside the exe
```

Validation at startup, all failures fatal:

- `SHUTDOWNER_PASSWORD_HASH` present and bcrypt-shaped
- `SHUTDOWNER_SESSION_SECRET` present and at least 32 bytes after hex decoding
- `SHUTDOWNER_LISTEN` parses and its host is a loopback address, unless
  `--allow-public-bind` is passed. This guards against a config typo turning
  `0.0.0.0` into an unauthenticated-path exposure of the power button.
- `SHUTDOWNER_DELAY_SECONDS` in `[0, 3600]`
- `SHUTDOWNER_SESSION_TTL` parses as a duration and is positive


## Error handling

- **Startup failures** exit non-zero and write to both the log file and the
  Windows Event Log. A service that dies silently at boot is otherwise invisible.
- **Panics** are caught by recovery middleware, logged with the stack, and
  returned as 500.
- **Login failure** returns a single generic message. There are no usernames, so
  enumeration is not a concern, but the message stays uniform regardless of cause.
- **Rate limited** returns 429 with `Retry-After`; the UI shows when to retry.
- **Action conflict** returns 409 and the UI re-renders the existing pending action.
- **Unsupported action** returns 400 with the capability reason.
- **Execution failure** moves the state machine to `Failed`, retaining the
  underlying error — a `shutdown.exe` exit code, or a `SetSuspendState` failure —
  and displays it in the UI rather than reporting a generic 500.

Logging uses `log/slog` to a file, since a service has no console. Rotation at
5 MB keeping 2 previous files, implemented as a small `io.Writer` wrapper rather
than by adding a logging dependency.

## Testing

Test-driven throughout: a failing test precedes each behaviour.

### Covered on Linux

- **config**: each required field missing; malformed hash; short secret;
  non-loopback listen rejected; non-loopback accepted with `--allow-public-bind`;
  delay and TTL bounds; defaults applied when optional keys are absent
- **auth**: correct and incorrect password; session sign and verify round trip;
  tampered payload rejected; wrong secret rejected; expired session rejected;
  malformed cookie rejected; CSRF token match and mismatch; rate limiter at 4, 5,
  and 6 failures; window expiry restoring access; global ceiling
- **action**: schedule from idle; schedule from failed; schedule while pending
  returns conflict; schedule sleep or hibernate without the capability returns
  unsupported; schedule shutdown and restart regardless of capabilities; abort
  with a matching id; abort with a stale id; abort when idle; timer firing calls
  the controller with the right action and force flag; controller error moves to
  `Failed`; `Failed` reverting to `Idle` after 60 seconds; sleep returning moves
  back to `Idle`; status snapshot values
- **power**: `buildShutdownArgs` for all four actions across both force values;
  `unsupported.go` returning `ErrUnsupported`
- **web**: unauthenticated GET `/` redirects; valid session renders; login success
  sets a cookie carrying all four required attributes; login failure re-renders
  with an error; a rate-limited login re-renders with 429; POST with no CSRF
  token returns 403; the token accepted from a header; the token accepted from a
  form field; `POST /login` exempt from CSRF; `/api/action` maps to a `Schedule`
  call; 409 and 400 propagate; `/healthz` needs no session; security headers
  present on every response

The `action` tests use the fake controller and an injected timer seam, so the
whole suite runs in well under a second with no real waiting.

### Not covered by automated tests

The Win32 calls in `power/windows.go`, `sysinfo/windows.go`, and the service
wrapper in `winsvc`. These stay deliberately thin, with all branching logic
extracted into the pure functions listed above. They are covered by a manual
checklist run on the target PC:

1. `--install-service`, reboot the PC, confirm the service is running before login
2. Reach the subdomain from a phone on cellular with Wi-Fi disabled
3. Six wrong passwords in a row produce a 429
4. Each of the four actions completes
5. Abort cancels each of the four actions
6. With hibernate disabled via `powercfg /h off`, the button renders disabled and
   the API returns 400
7. With an unsaved Notepad open: forced shutdown completes; graceful shutdown is
   blocked by Windows and the UI reflects that the PC is still up
8. Log file is written and rotates

### Development on Linux

`--fake-power` runs the real server with the fake controller, so login,
countdown, abort, and status polling are exercised end to end on the development
machine before any binary is copied to Windows.

## Build and deployment

```
GOOS=windows GOARCH=amd64 CGO_ENABLED=0 go build -ldflags "-s -w" \
    -o dist/shutdowner.exe ./cmd/shutdowner
```

Makefile targets: `test`, `vet`, `build-windows`, `run-dev`.

Dependencies, three in total:

- `golang.org/x/crypto` — bcrypt
- `golang.org/x/sys` — Win32 syscalls and the service framework
- `github.com/joho/godotenv` — `.env` parsing

Everything else is standard library.

`.gitignore` covers `.env` and `dist/`. `.env.example` is committed.

Installation on the target PC:

1. Copy `shutdowner.exe` to `C:\Program Files\Shutdowner\`
2. `shutdowner.exe --init`
3. `shutdowner.exe --hash-password` and paste the result into `.env`
4. `shutdowner.exe --install-service`
5. Install cloudflared, create a tunnel, route the subdomain to
   `http://127.0.0.1:8080`

## Out of scope

Deliberately excluded to keep this to one implementation cycle:

- Wake-on-LAN and any form of powering the machine on
- Controlling more than one machine from a single instance
- Multiple users, usernames, or role separation
- Two-factor authentication
- A persisted audit log of past actions
- Scheduled or recurring actions
- Windows Event Log as a general logging sink beyond startup failures
